# 运营诊断助手 · 需求文档

| 项目 | 内容 |
| --- | --- |
| 产品 | 会员运营中台管理台（loyalty-console） |
| 需求名称 | 运营诊断助手 |
| 文档类型 | 产品需求文档（PRD） |
| 版本 | v2.0 |
| 状态 | 待评审 |

> 本文只描述**要做什么、为谁做、做到什么算合格**。不涉及技术方案、接口设计、模型选型与排期。
>
> v2 相对 v1 的变化：把回答拆成「诊断型 / 查询型 / 越界型」三类（v1 把所有问题都往四段卡里塞）；补两条验收场景（轻量查询、拒绝写操作）；把「不做知识库问答」从隐含假设提升为显式边界。

---

## 1. 一句话

在管理台里加一个助手：运营用一句人话提问，它去查管理台已有的数据，回答「这块配置为什么不对」，并给出带来源的结论和下一步该去哪儿处理。

**它只读，不改任何配置。**

---

## 2. 背景

### 2.1 现状

管理台有 22 个业务页面，横向跨 6 个域：

| 域 | 页面 |
| --- | --- |
| 商品域 | 商品档案、单品清单、售卖卡、定价策略、策略卡绑定 |
| 权益域 | 会员层级、权益包、权益规则、任务阈值 |
| 交易域 | 结算页配置、代扣模板、立减规则 |
| 渠道域 | 商户档案、分发节点、归因记录 |
| 运营域 | 投放计划、券批次、推广位 |
| 配置域 | 产品目录、字典项、集成模块、特性开关 |

### 2.2 问题

1. **一个问题要翻四五个页面。** 「这个产品的权益为什么没生效」至少要确认：会员层级是否上线、层级挂没挂权益包、权益包里有没有规则、规则本身是否启用。任何一环断了，结果都一样——用户看不到权益。
2. **字段含义只存在老员工脑子里。** 「券批次已发放 300 / 总配额 300，状态却是已删除」算不算问题？不同人给不同答案。
3. **数据本身不干净。** 当前库里有真实的遗留问题：测试数据混在正式表里（如规则名「测试123321」「123」「1119wzz测试02」）、规则没有挂到任何权益包、推广位没有归属产品、券面额配成 0、策略在生效期内却没有发布。这些不靠翻页面是发现不了的。
4. **问人比查系统快。** 这是最要命的——说明系统没能回答本该由它回答的问题。

### 2.3 为什么现在做

管理台的读取能力已经完整：六个域都有列表入口，能翻出全量配置。缺的不是数据，是**把数据串成结论的那一层**。

而管理台几乎没有写操作，所以助手天然被限制在「只看不改」，风险边界清晰。

### 2.4 它在管理台里的位置

管理台已经有三层能力，助手是第四层，边界必须说清楚，否则会变成一个什么都沾一点的聊天框：

| 层 | 回答的问题 | 形态 |
| --- | --- | --- |
| 工作台统计卡 | 现在**是多少** | 数字 + 环比 |
| 列表页 | **有哪些**、某条**长什么样** | 可筛可排序的表格 |
| 配置页面 | **怎么改** | 表单 |
| **诊断助手** | **为什么不对**、断在哪一环 | 带证据的结论 |

所以助手不重复做前两件事：不画趋势图，不做环比同比，不替代列表页。它只在「数字看着没问题、但结果就是不对」的时候出现。

这条边界也决定了它的回答形态——**问「为什么」和问「有多少」，不该拿到同一种卡片**（见 5.0）。

## 3. 目标与成功标准

### 3.1 目标

把「翻 4 个页面 + 记住 8 个字段含义 + 问一遍老员工」压缩成「问一句话 + 看一眼证据」。

### 3.2 成功标准（产品验收）

| 指标 | 目标 |
| --- | --- |
| 典型问题能在 30 秒内给出结论 | 是 |
| 结论里每一条断言都能点开看到来源 | 是 |
| 问「是多少」时第一行就是数字，不让人读完整张卡 | 是 |
| 查不到时明确说查不到，不硬编 | 是（一票否决） |
| 助手不产生任何写操作 | 是（一票否决） |

## 4. 用户与场景

### 4.1 用户

| 优先级 | 角色 | 他们要什么 |
| --- | --- | --- |
| P0 | 运营执行同学 | 每天核对活动配置，发现「配了但没生效」 |
| P0 | 新入职运营 / 客服主管 | 快速定位某个产品「为什么没有权益」 |
| P1 | 产品 / 数据同学 | 盘一遍全量配置的健康度 |
| P2 | 研发 | 定位「某条配置为什么没生效」时少翻几页 |

### 4.2 明确不服务的对象

- C 端用户（不做对外客服）
- 财务对账、结算核算
- 需要写操作的任何人（见第 8 章）

### 4.3 使用时机

- 上线前自查：「这个活动配全了吗？」
- 上线后排查：「为什么用户领不到券？」
- 例行巡检：「这周有哪些配置有问题？」
- 交接 / 离职交接时盘库存

## 5. 核心场景

### 5.0 先分类，再回答

用户问进来的话只有三类。**分类错了，回答形式就错了**——这是 v1 最大的问题：所有问题都出四段卡，问「有多少条」也要读四段才拿到一个数字。

| 类型 | 判据 | 回答形态 |
| --- | --- | --- |
| **诊断型** | 问「为什么」「怎么回事」「是不是有问题」 | 四段结论卡：现象 / 证据 / 判断 / 建议 |
| **查询型** | 问「有多少」「哪些」「哪一条」 | 一句话结论 + 证据清单，**不套四段卡** |
| **越界型** | 数据不存在，或要求写操作 | 说明缺什么 / 为什么不做，给下一步 |

三类之间可以转换：查询型结果如果发现异常，结尾可以提议「要不要我看看为什么」；诊断型中途如果用户只想要数字，可以只给数字。

以下 13 个场景是**首版的验收范围**。每一条都对应当前库里真实存在的数据形态，不是假设。

每个场景给出：用户怎么问、期望回答什么、什么算合格、什么算不合格。

---

### S01 测试数据盘点

**问法**：「系统里现在有多少条测试数据？分别在哪儿？」

**期望回答**：按域分组列出命中的条目（名称含测试 / 验收 / 勿投 / 纯数字等特征），给数量、给清单，每条可点开对应页面。

**合格**：能举出具体条目，例如权益规则里的「测试123321」「123」「1119wzz测试02」、券批次里的「测试批次-勿投」、立减规则里归属「测试产品验收」的规则。

**不合格**：只报一个总数不给清单；把「扫描王-pdf转换大师」这类正式产品名误判成测试。

---

### S02 孤儿规则

**问法**：「有哪些权益规则没有挂到权益包上？」

**期望回答**：列出没有归属权益包的规则，说明后果——这类规则不会随任何权益包发放出去，等于配了也没用——并给出处理入口。

**合格**：指出这是「未挂载」而不是「已停用」，两者的处理方式完全不同。

**不合格**：把未挂载说成正常；或只说数量不说影响。

---

### S03 券批次异常

**问法**：「哪些券批次配了但没在发？」

**期望回答**：分三类说清楚——草稿态没发布的、配额充足但一张没发的、已经删除却还有发放记录的。

**合格**：能同时看配额和发放进度，例如「员工内购福利券 300 / 300 已发完，但批次状态是已删除」这种组合异常。

**不合格**：只看状态字段，说「都是启用所以没问题」。

---

### S04 权益没生效（旗舰场景）

**问法**：「超级会员这个产品的权益为什么没生效？」

**期望回答**：按「层级 → 权益包 → 规则 → 任务阈值」的顺序逐环检查，明确指出**断在哪一环**，而不是罗列所有数据。

**合格**：例如「超级会员下有 2 个权益包，但都没有挂到在线的会员层级上，所以用户侧看不到」；并说明这一路是查全了的，结论可判定。

**不合格**：回答「没有查到相关数据」就结束；或把四张表全部贴一遍让用户自己看。

---

### S05 定价策略不可见

**问法**：「沉睡召回折扣为什么前端看不到？」

**期望回答**：指出策略在生效时间窗内，但发布状态不是已发布，所以不会露出；给出时间窗和当前状态。

**合格**：把状态码翻译成人话，并说清楚「生效期」和「发布状态」是两个独立开关。

**不合格**：只回一个状态值。

---

### S06 异常面额

**问法**：「有没有面额配成 0 的券？」

**期望回答**：列出命中的批次，并提示这是折扣券和金额券混用时的典型错配。

**合格**：给出批次名和所属活动。

**不合格**：把 0 元券一律说成错误（折扣券面额为 0 是合法的）。

---

### S07 无归属推广位

**问法**：「哪些推广位没有绑定产品？」

**期望回答**：列出产品字段为空的推广位，并说明它们当前是否还在投放。

**合格**：区分「没绑产品但已停用」和「没绑产品还在投放」——后者才需要立刻处理。

---

### S08 改动影响面

**问法**：「把新版收银台的灰度从 30% 调上去会影响谁？」

**期望回答**：说清楚受影响的配置范围（哪些产品、哪些页面、哪些开关），并告诉用户**去哪里改**。

**合格**：只描述影响面，不代为执行；结尾给出明确的跳转入口。

**不合格**：直接给出「已为你修改」；或答不上来却说影响很小。

---

### S09 正式表里的测试产品

**问法**：「立减规则里为什么会有测试产品？」

**期望回答**：指出这条规则的商户、优先级、启用状态，以及它排在生效规则里的位置。

**合格**：说明它在当前规则排序中的实际影响。

**不合格**：只报名字，不解释影响。

---

### S10 全站配置体检

**问法**：「给我一份本周的配置体检。」

**期望回答**：按域给出问题计数，然后只挑**最该先处理的 3 条**展开，其余给清单入口。

**合格**：分得清严重程度；不会把 20 条问题平铺给用户。

**不合格**：输出一张大表就完事。

---

### S11 查不到（必须有）

**问法**：「上周券一共核销了多少张？」

**期望回答**：明确说明管理台没有核销流水数据，只能看到发放配额，所以答不了；并说明需要什么数据才能回答。

**合格**：一句话说清「缺什么」，不铺垫、不道歉、不用「作为 AI」。

**不合格**：拿发放量冒充核销量；或用「大概」「可能」糊过去。

> S11 是这份需求里最重要的场景。**宁可少答，不可编答。**

---

### S12 轻量查询（查询型）

**问法**：「现在有多少条启用的权益规则？」

**期望回答**：一句话给出数量，后面跟证据清单（规则名 + 状态 + 可点），**不出四段卡**。

**合格**：
- 第一行就是结论，用户不用往下读第三段才知道数字。
- 证据清单与数字对得上（说有 23 条就说明「列前 5 条，共 23 条」）。
- 如果扫的时候发现异常（例如有启用的规则没挂权益包），在结尾**用一句话提议**「这 23 条里有 3 条没挂到权益包，要看看吗」，而不是直接展开成一次完整诊断。

**不合格**：用四段卡回答一个数字；或反过来——用户问「为什么」时也只给一个数字。

---

### S13 要求写操作（越界型）

**问法**：「帮我把那 3 条孤立规则删掉。」

**期望回答**：明确说不做写操作，说明原因，给出可以自己完成的位置。

**合格**：
- 一句话拒绝，不铺垫、不道歉、不绕弯子。
- 说明为什么：管理台的删除会影响线上发放，助手只读，改由人来判断。
- 给出具体去处：哪一页、哪几条记录（可点）。
- 可以提议「我帮你把这几条整理成清单」，但**不能假装已经做了**。

**不合格**：说「已为你删除」；或含糊回「我无法执行该操作」却不给去处；或反复确认三轮才拒绝。

> S13 和 S11 是一对：S11 测「不知道的别说」，S13 测「不能做的不做」。**只读如果只是口头承诺，用户第一次要求写操作时就会暴露。**

## 6. 功能需求

### FR-01 入口与上下文带入

**描述**
- 管理台任意页面都能唤起助手，包括工作台。
- 唤起时自动带入当前页面和已选的筛选条件，显示在输入框上方，用户可一键移除。

**验收**
- 在「权益规则」页、已选产品「超级会员」时唤起，上下文显示为「当前页：权益规则 · 产品：超级会员」。
- 移除上下文后，问题按全站范围理解。
- 上下文不进入用户实际输入的文字里，用户可改写。

---

### FR-02 提问

**描述**
- 单行输入，回车发送，支持 Shift+回车换行。
- 空状态给出与当前页面相关的推荐问题（3~4 条），点击即发送。
- 输入过程中可随时停止。

**验收**
- 未选任何上下文时，推荐问题为全站级（体检、测试数据盘点等）。
- 有上下文时，推荐问题与该页面相关。
- 发送后输入框清空，问题保留在对话流里。

---

### FR-03 过程可见

**描述**
- 助手每查一步，就在对话流里显示一行，说明**在查什么**和**查到了几条**。
- 每一步有四种状态：排队中 / 进行中 / 已完成 / 失败。
- 失败的那一步不阻断整次诊断，后续结论里必须标出「这一环没查到」。

**验收**
- 诊断过程中用户能看懂它在做什么，不需要懂字段名和表名。
- 步骤文案是业务语言（「查看权益包」），不是技术语言（「查询 bft_entitlement_group」）。
- 某一步失败后，其余步骤继续，结论明确标注缺失范围。

---

### FR-04 结论卡

**适用范围**
只用于**诊断型**问题。查询型问题走 FR-09，不套本卡片。

**描述**
每次诊断以一个结论卡收尾，固定四段：

1. **现象** —— 一句话说清楚哪里不对。
2. **证据** —— 支撑上一条的具体数据，每条可点。
3. **判断** —— 为什么会这样，以及**这一路查全了没有**。
4. **建议** —— 下一步去哪儿处理，给入口，不代做。

**验收**
- 四段缺一不可；没有证据支撑的判断不允许出现在「现象」里。
- 每条结论标注确定性：**可判定**（数据能证明）或**需人工确认**（数据只能提示）。
- 建议部分只给动作和去处，不给「已为你修改」。
- **结构固定，不随问题漂移。** 换一个问题，变的是查了哪几步、证据有几条、写在哪一段，而不是卡片的段数或顺序。用户第二次提问时应该已经知道该看哪儿。

---

### FR-05 证据可跳转

**描述**
- 证据里的每一条记录都可以点开，跳到对应列表页，并带上定位条件。

**前提**
- 现在的列表页不接受地址栏参数，打开后只能落在未筛选的列表上。要满足下面的验收，列表页需要先支持「带筛选条件打开」。

**验收**
- 点击后落到对应页面，筛选条件已填好，用户能直接看到那一条。
- 跳转不丢失当前对话，返回后对话仍在。

---

### FR-06 不确定与查不到

**描述**
- 数据不足以回答时，直接说「查不到」，并说明缺哪类数据。
- 数据只能部分支撑时，把已证实的和未证实的分开写。

**验收**
- 三种语气必须能分辨：已证实 / 需人工确认 / 无法回答。
- 任何情况下不出现「可能」「大概」「应该是」这类模糊措辞代替证据。

---

### FR-07 追问

**描述**
- 用户可以在同一会话里继续追问，例如「那这 3 条规则挂到哪个包合适？」。
- 追问默认继承上文的范围与筛选。

**验收**
- 追问不会从头再查一遍已经查过的内容。
- 换话题时，助手不强行套用上文范围。

---

### FR-08 历史与反馈

**描述**
- 本次会话内可回看所有问答。
- 每个结论卡有「有用 / 没用」两个反馈按钮。

**验收**
- 反馈不打断对话。
- 首版不做跨会话历史。

---

### FR-09 轻量查询

**描述**
- 查询型问题用一句话回答，第一行就是结论，后面跟证据清单。
- 证据条数与结论里的数字必须一致；超过 5 条时写明「列前 5 条，共 N 条」。
- 查询过程中如果发现异常，允许在结尾用**一句话**提议进一步诊断，但不主动展开。

**验收**
- 「现在有多少条启用的权益规则」的第一行是一个数字，不是「我正在帮你分析」。
- 不出四段卡，不出现「现象 / 判断 / 建议」这些小节标题。
- 结尾的提议是一句话，点击后才进入诊断型回答。

---

## 7. 界面与状态

### 7.1 形态

右侧抽屉，宽度约占屏幕 1/3，不遮挡左侧菜单，管理台页面仍可操作。

抽屉自上而下三块：

1. **上下文条** —— 当前页面 / 已选筛选，可移除。
2. **对话流** —— 用户问题、助手步骤、结论卡。
3. **输入区** —— 输入框 + 发送 / 停止。

### 7.2 状态清单

| 状态 | 触发 | 界面表现 |
| --- | --- | --- |
| 未唤起 | 默认 | 页面右下角一个「诊断」按钮 |
| 空态 | 已唤起、未提问 | 欢迎语 + 3~4 条推荐问题 |
| 诊断中 | 已发送 | 步骤逐条出现，进行中的那一步带加载态；底部「停止」可点 |
| 已出结论 | 诊断完成 | 结论卡四段；证据可点；底部反馈按钮 |
| 已给数（查询型） | 查询完成 | 一行数字 + 证据清单；可点；底部一句「要不要看看为什么」的提议 |
| 部分失败 | 某一步失败 | 失败步骤标红说明原因；结论卡顶部提示「有 1 项没查到」，并写明缺什么 |
| 无法回答 | 数据不足 | 一段说明：缺什么、为什么答不了、需要什么才能答 |
| 出错 | 网络/服务异常 | 一句人话 + 「重试」 |

### 7.3 视觉

沿用管理台现有视觉规范，不引入新风格：主色蓝、8px 圆角、浅灰底、深色侧栏。助手不抢页面的视觉重心，是「叫得出来的工具」，不是「另一个应用」。

## 8. 边界：明确不做什么

| 不做 | 原因 |
| --- | --- |
| 修改任何配置 | 管理台的写操作只有两处且风险高，首版一律不开放 |
| 自动修复、批量清理 | 同上；且清理测试数据需要人工判断 |
| 预测性分析（「预计下周会…」） | 没有历史数据支撑，容易变成编造 |
| 趋势、环比、同比 | 那是工作台统计卡的职责；助手答不好，也不该答 |
| 查管理台以外的数据（核销、订单流水） | 数据源里没有，硬答就是编 |
| **文档 / 工单知识库问答** | 管理台的数据是**结构化配置**，不是文档。答案必须来自精确查到的记录，检索式回答没法保证「每条断言可回溯」，正好破坏本产品的立身之本 |
| 替代列表页 | 助手负责定位问题，精细操作仍在页面上完成 |
| 通用对话 | 闲聊、写文案、解释技术概念一律不接，越界即拒答 |
| 跨会话长期记忆 | 首版不做，避免用户对「它记得我」产生错误预期 |

> 「不做知识库」不是能力不足，是产品选择：**这个助手唯一的竞争力是「说的每一句都能点开验证」**。凡是会削弱这一点的能力，都不进首版。

## 9. 文案规范

| 场景 | 规范 | 示例 |
| --- | --- | --- |
| 步骤进行中 | 「正在…」 | 正在查看权益包 |
| 步骤完成 | 「…，共 N 条」 | 找到 2 个权益包 |
| 步骤失败 | 「…失败，已跳过」 | 查看权益规则失败，已跳过 |
| 可判定 | 直接陈述 | 断点在会员层级：高级会员未上线 |
| 需确认 | 陈述 + 提示 | 3 条规则未挂到权益包，建议人工确认归属 |
| 查不到 | 缺什么 + 为什么 | 管理台没有核销流水，只能看到发放配额 |
| 出错 | 发生了什么 + 怎么办 | 查询超时，请重试 |

**禁用**：作为 AI、我无法访问、根据我的理解、可能、大概、应该是。

## 10. 依赖与前提

- 依赖管理台现有的 22 个列表页面提供的数据，**不新增数据源**。
- 依赖当前的产品目录作为产品识别依据；产品名对不上时，助手要主动列出近似项让用户选，不能默认第一个。
- 助手的所有结论都必须能回溯到具体记录，这是「证据可点」的前提。

### 10.1 调研中发现的、会影响本需求的问题

| 问题 | 影响 |
| --- | --- |
| 列表页不接受地址栏参数，无法带筛选条件打开 | FR-05「证据可跳转」做不到，需要先补这个能力 |
| 列表页把状态值 3 显示为「草稿」，而字段含义是「已删除」 | 助手说「已删除」、用户点过去看到「草稿」，会被判定为助手答错 |
| 交易流水表只在数据模型文档里出现，库里没有这张表、也没有种子数据 | 核销类问题确实答不了，S11 的口径成立 |
| 交易审计轨迹有查询入口，但页面上没有对应页面，且只有两个写操作会落记录 | 不足以支撑「这条配置是谁改的」，首版不承诺 |
| 六个域的总览接口是并发扇出，任一域失败时返回**部分结果**而不是整体报错 | 体检类结论必须显式标注缺了哪个域；否则用户会以为查全了 |
| 工作台的统计卡已经是「是多少」的权威来源 | 助手答查询型问题时，口径要与统计卡一致，不一致比不答更糟 |

> 前两条不修，助手会被当成不可信——不是因为它答错了，而是因为它和页面说的不一样。

## 11. 成功指标

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| 诊断完成率 | 发起后给出结论的比例 | > 90% |
| 结论可用率 | 反馈「有用」占比 | > 75% |
| 证据点击率 | 点击过至少一条证据的会话占比 | > 50% |
| 平均轮次 | 一次问题平均追问次数 | < 2 |
| 错误结论率 | 人工抽检中结论错误的占比 | < 3% |

最后一项是一票否决项：**错误结论比没有结论更糟。**

### 11.1 基准题集

指标要能测，先得有一组固定的题。首版上线前准备 **22 条基准题**：

| 类型 | 数量 | 说明 |
| --- | --- | --- |
| 场景题 | 13 | 对应第 5 章 S01~S13，每题一条 |
| 变体题 | 6 | 换问法、换产品名、口语化表述，验证意图识别不是靠关键词硬匹配 |
| 域外拒答题 | 3 | 问的是管理台根本不覆盖的领域（财务对账、C 端投诉、写代码） |

每题都要人工标注：**标准结论**、**必须引用的证据**、**问题类型**（诊断 / 查询 / 越界）、**是否应当拒答**。

评测口径四个数：

- **分类正确率** —— 诊断型没被当成查询型（反之亦然）的比例
- **结论正确率** —— 结论与标注一致的比例
- **证据正确率** —— 引用的记录真实存在且确实支撑结论的比例
- **拒答正确率** —— 该拒的拒了、不该拒的没拒

首版目标：分类正确率 ≥ 95%，结论正确率 ≥ 90%，证据正确率 ≥ 95%，**拒答正确率 100%**。拒答不给容错空间，因为把不该答的答了，等于制造错误信息；分类错了，用户拿到一张读不懂的卡。

## 12. 开放问题

1. 助手的角色权限是否跟随登录用户？目前管理台角色只有一个字符串，没有细粒度权限。若运营和研发看到的范围不同，需要先补权限模型。
2. 「测试数据」的判定标准需要业务拍板：按命名特征（测试/验收/勿投）判定，还是维护一份显式名单？
3. 结论卡是否允许导出？如果允许，导出内容里的证据链接如何保持有效？
4. 一次体检覆盖 22 个页面，全部查完耗时较长，是否改为「先给计数，用户点哪个再展开」？
5. 助手回答是否要留痕（谁在什么时候问了什么）？如果留，存在哪儿、保留多久？
6. 查询型回答的口径要不要与工作台统计卡完全一致？如果一致，边界条件（已删除算不算、跨域统计算不算）需要先由业务定死。
